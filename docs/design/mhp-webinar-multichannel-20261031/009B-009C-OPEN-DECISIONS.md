# 009B/009C clarification for source review — 1 November 2026

This note accompanies the byte-identical local 009B design and its selection records. It distinguishes decisions already selected by Astra from questions that still require a recorded Astra decision. It does not authorise a migration, code change, provider send or cap increase. There is no separately ratified 009C SQL design in this handoff.

1. **Scheduled SMS authority — selected in 009B.** The due worker uses a new, exclusive `mhp_event` authority and job provenance branch, derived from a real owner's earlier approval of the exact recipient batch and current event permission. It does not call the human-only `authorize_and_enqueue_sms_live_job`, claim a current owner permission-use receipt, or extend that receipt beyond the existing five-minute bound. Section 7 of `009B-SQL-DESIGN.md` specifies the proposed additive/guarded changes to `app.property_predator_sms_authorities`, `property_predator_sms_jobs` and the event claim/begin functions. The original `owner_action` branch and 0032 human permission-use CHECK remain intact; any new 0032/0056 function or constraint bytes require Astra's source ratification and real-caller proof before release.

2. **Signed STOP before contact linking — open.** The 009B design describes event-specific withdrawal after an established point, but does not specify durable STOP handling when a signed SMS arrives from a number with no contact point, such as a reply to a verification text. It also does not specify the 0055 WhatsApp STOP projection change. Claude must not treat an unlinked STOP as an unknown number to ignore, create a marketing contact solely from STOP, or infer WhatsApp opt-out from an SMS opt-out. Astra must decide the minimal signed-ingress suppression key and projection/lookup contract, including whether and how the existing 0056 and 0055 inbound functions may be changed. Until that is ratified and tested, this remains a release blocker for the relevant channel.

3. **WhatsApp frequency, verification and template read — partly selected, partly open.** Existing 0053 limits are one send per workspace per day and three per workspace per month; `009B-EVENT-PHONE-DESIGN.md` explicitly retains them. They do not support an audience-scale webinar follow-up. No higher caps or combined SMS/WhatsApp frequency are approved by these documents; Astra and the founder must decide a bounded policy before 009C can promise more. WhatsApp possession proof is a separate user-sent JOIN through `wa.me`, verified by the existing app-secret-HMAC inbound path against the exact MHP WABA, phone ID, sender and nonce. It is not an SMS receipt or an authentication-category template. The proposed reminder template is `mhp_webinar_20261104_reminder_v1`, ID `1441099094827445`, `en_GB`, Marketing; it was still **In review** at the last Meta check. The design requires a server-side read of Meta's actual approved template, including status and exact components, at activation and before send. It does not yet name the process, Graph API operation, or MHP-scoped token custody/read permission. Astra must ratify that boundary; no owner-entered “approved” flag can substitute for the provider read.

The original `009B-SQL-DESIGN.md` remains unchanged. Claude's 009B/009C candidates are source work for review, not ratified releases; nothing in this note deploys them.
