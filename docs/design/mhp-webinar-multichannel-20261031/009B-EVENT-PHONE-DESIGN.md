### Replay, changes and identity collisions

- Request command replay compares full canonical payload before creating another token/mail. Mail unknown outcome is held; do not resend automatically. A new explicit request after cooldown may issue a new token and supersede the prior unconsumed one.
- Technical abuse limits propose reuse of existing admission infrastructure plus max3 requests/hour per event+email/source and per event+phone,60second resend cooldown; these are challenge controls, not a new message-frequency or retention policy. No outbound SMS OTP/pumping cost. High entropy nonce has no brute-force-friendly short code; invalid JOIN responses remain generic.
- Email access proves control of the registered mailbox, not legal identity. Signed inbound proves a usable endpoint at that moment, not permanent ownership. Existing contact dedupe index and endpoint hash stay authoritative.
- Resolve contact by existing event/prospect mapping; if absent, by a single normal active matching email point. If email or phone points resolve to different contacts, shared/quarantined points, multiple active rows or another brand: hold for owner resolution, never merge/move/overwrite silently. If neither exists, closed projection creates one existing contact with source `mhp:event-phone:<event>` and provenance mapping; no opportunity required for possession proof. Existing CRM owner can later assign/manage it.
- Repeated signed inbound same provider SID+exact hashes returns exact prior receipt and no new grant/contact/message/job. Same SID with different payload is conflict. Multiple JOIN deliveries serialize at intent/phone; only one current receipt per event+channel+point. A second prospect claiming the same active event point is a conflict, not a silent identity swap.
- Changing the number creates a new intent revision and invalidates old pending JOIN nonce. It cannot edit an immutable verification/permission receipt. Explicitly supersede the former event grant for future preparation; accepted/unknown delivery history remains. Both old and new cannot be active silently.
- Concurrent withdrawal/STOP wins at the current eligibility check. A previously recorded JOIN replay cannot re-grant after withdrawal. New event opt-in requires a new intent+new signed proof and still cannot clear suppression.
- No new retention duration is invented. Keep only required token hash/expiry, event linkage, consent/proof hashes and existing CRM identity. Raw tokens/nonces are not logs. Mark expired/consumed; deletion/retention stays with existing rules/owner policy. Any cleanup schedule beyond that is a separate explicit decision.

## Provider expiry and copy are separate from authority

Root's observed MHP Messaging Service validity defaults to36000seconds. Current adapter omits per-message validity. Proposed narrowly optional event request field `providerExpiresAt` is read ONLY from the server-bound event authority; legacy request behavior is unchanged. Immediately before request, compute integer ValidityPeriod from remaining provider deadline, refuse nonpositive, and send bounded value1..36000. Do not change the whole service default or another brand. Freeze the absolute deadline/idempotent request binding; a retry cannot obtain a later deadline.

Twilio documents that validity limits its platform queue, not a guaranteed handset arrival time. It does not recall a message already handed to a carrier. The UI can honestly promise “we stop submitting after the event cutoff,” not “your phone can never receive a late text.” Use neutral dated copy, e.g. owner-reviewed draft: “Martin Howard Property: webinar Wed4Nov at7:30pm UK. Watch: https://martinhowardproperty.co.uk/webinar/live/ . Reply STOP to stop texts.” GSM/segment preview must compute actual length; do not claim one segment without checking actual final text. No “starts in one hour” if delivery can be delayed.
