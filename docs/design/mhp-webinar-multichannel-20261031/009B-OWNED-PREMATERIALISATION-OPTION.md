Read-only reduction requested by Astra after reviewing design af68e309e563bc5ed609bdca5a07d1c593fe081e4953d27fafa11466ada01366. That document remains unchanged/historical. Baseline is still R10e3a846/tree89fe6/schema130e6bb. No app/test/SQL/provider changes or checks executed.

## Result: viable for one already verified, explicitly approved event recipient

Yes: actual owner activation can pre-materialise the exact LIVE message, immutable version, human approval request and decision, AND delivery/provider-operation records. This removes the proposed new nullable delivery-creator/per-message-approval branch for this first vertical. Existing approval tables and delivery approval FKs can remain unchanged. It does not remove the genuine event worker-authority gap, and it cannot serve later automatic public entrants without another real approval mechanism.

This is a source-contract conclusion, not a database proof or implementation ratification. The following exact path must be proved under the real roles/guard triggers in isolation before use.

## Exact call map and why it can work

1. Recipient first has actual event-registration identity, verified endpoint and a NEW explicit event SMS permission receipt. Old one-test consent is not reused. This option does not itself change the approved identity/verification design or claim public verification exists. The selected first recipient is genuinely owned/allowlisted.
2. Native owner activates ONE exact event reminder for THAT recipient under their real MHP session, selected workspace, current user/request, Origin and CSRF. The new closed owner operation validates current event receipt, sender, source/version/hash, date/window, latest programme approval, suppression and current owner membership. Existing app.command_receipts records the full activation payload and actual actor; history replay occurs before mutable checks.
3. Reuse the actual0130 lifecycle operations WITHOUT calling its self-test producer: message draft → immutable version → approval request → approval_pending → real human decision → approved. The owner is actually reviewing this recipient/body/date and authorising later automation now. Existing message/version source_content_* bind the real0021source and owner approval. No fabricated worker-as-owner context or invented decision at due time.
4. Owner operation can insert provider operation as queued and LIVE delivery as queued, in the SAME transaction, using the existing0056 SMS delivery guard exactly. The delivery's created_by_user_id is honestly this current owner. The operation/delivery mutually referencing FKs are already used by0056's insert order. Then reserve the operation exactly as0056 does: state=reconciliation_required, next_attempt_at=infinity, last_error_code=twilio_sms_live_reserved, no provider reference; commit message lifecycle=committed. Attach these exact records to the scheduled calendar metadata and actual event approval. Create NO SMS authority or SMS job yet.
5. At the absolute due time the new closed worker function uses actor_kind=worker/user empty, revalidates current event receipt/current point/source/owner programme/sender/caps and derives fresh fixed short event authority, then inserts ONE existing SMS job against that pre-existing delivery/operation. The genuine human approval and creator are historical immutable facts; the new authority/queue insertion must explicitly record actual worker provenance. It cannot call the human-only authorize_and_enqueue_sms_live_job or reuse the expired activation permission-use receipt as current authority.
6. Claim/load/begin use a narrow event-authority branch that checks the pre-materialised exact message approval and current event grant plus current endpoint/suppression/binding/event deadline/caps. Existing transport/lease/settlement/STOP and per-request TTL plan remain reused. No second body, CRM or transport queue.

## Smallest remaining schema/source scope if Astra chooses this option

- Omit all proposed delivery-creator/per-message approval nullable/discriminator changes from the broad af68 option. Existing approval request/decision/delivery tables need no shape change for the first recipient. Owner activation pre-materialises those records before scheduled execution.
- Keep a minimal immutable event permission/verification linkage and existing absolute calendar row carrying real activation command/actor/request and exact pre-materialised message/version/request/decision/delivery/provider-operation IDs, source/body/endpoint hashes, event/window/sender/prospect/point. No new body/transport store.
- Keep narrow event authority provenance and genuine worker job-creation provenance. Owner authority's original complete human-only fields remain required. New event worker eligibility is an explicit separate branch bound to actual owner activation and current event permission, not a pretend human permission receipt. Exact proposed columns/nullability/shape/guards/roles still require the next SQL design gate.
- At due, worker does not need INSERT on messages/message_versions/message_approval_requests/message_approval_decisions/message_deliveries. It only reads their exact immutable linkage, then creates the fresh event authority and one job. This is a material privilege reduction.
- Current consent/point identity at due must match the owner's approved tuple. A new number/new consent revision/different source after activation holds the step and requires a NEW actual owner review; no automatic rebinding. A new source draft holds the scheduled operation before queueing. STOP does not delete the approved records; it prevents authority/job/begin.
- Hold/cancel recovery has to account for pre-materialised committed message+reserved delivery without a job: mark the scheduled step held/cancelled, reserve operation from all generic claims, never label it sent/unknown. Existing real submission is still derived only from a job/provider receipt. A restored old runtime must not pick up these deliveries through another provider rail.
- Future/public automatic entrants are expressly excluded from this reduction. Each additional recipient requires a genuine owner activation/pre-materialisation unless a separately approved automatic programme-authority design is implemented. Do not silently market this as automatic enrolment for all website leads.
