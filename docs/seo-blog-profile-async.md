# Background profile extraction — ASYNC008

Base: released `102aa2fda66684fa347556eea285a57aba4d414a`; migrations remain 0001–0135.

Brand setup submits an authenticated, CSRF-protected owner command and redirects immediately. The existing durable SEO queue stores `kind=write`, `payload.stage=profile`; UI labels it **Profile extraction**. The existing worker handles the explicit stage before article writing. Unstaged legacy jobs retain their handler; unknown stages are blocked. Setup shows queued/running/result/error status and an explicit review link. Polling reads status only: it never reloads the page, changes unsaved edits, submits extraction or confirms a profile. Without JavaScript, Refresh status and Activity provide the same durable result.

Each form command has a UUID. Active brand work coalesces and records command aliases, so exact replays find their original job even after its completion or a budget/source change. A genuinely new command can restart cancelled, unstarted work. Admission captures the full profile version/digest, readable document IDs/versions/hashes, brand context and prompt version/hash/resolved model. Current owner eligibility, exact input identity and unchanged preflight headroom are rechecked before model work. The worker retains its actual worker principal; it never becomes the requesting user.

The short persistence boundary locks brand, sources and jobs in a consistent order. Knowledge upload/retire and profile edit/confirm inserts share the brand lock. No provider call occurs in a database transaction. A durable provider-start nonce precedes generation. An expired started operation without a receipt becomes **blocked / outcome unknown**, rather than repeating a paid call. Generic Retry cannot clear this marker. A new extraction requires a separate owner command and explicit acknowledgement that the earlier call may have used tokens.

Completion atomically saves its nonce-bound receipt, actual known input/output usage once, an immutable **unconfirmed** profile and the job result. Applying a result requires the current lease owner and monotonically increasing claim epoch, unexpired lease, eligible requester and matching source/profile snapshot. A late cancelled/stale/expired result can account known usage and retain its receipt without replacing current edits or reviving cancelled work. A known receipt retries database completion only; it never invokes the model again. Applying a held saved result likewise uses the receipt, subject to the same current-input guards. If no receipt can be recovered after interruption, actual token use remains uncertain and is described as such.
