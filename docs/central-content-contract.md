Publication approval, policy, website connection, missed-slot and exact-version checks stay intact.

Workers do not impersonate an owner to call canonical company-content commands. Generic social account binding and dispatch must resolve the selected brand's actual connected account and preserve existing exact approval/provider/cap boundaries. PP startup defaults are never inherited by a new brand. Any missing connection is a truthful hold, not a claim that a prepared draft was scheduled or published. ### Owner Approve promotion (real, no import chore)

`approvePromotion` records a durable **owner observation** on the article (`promotionObservations`: purpose, version, network, pack digest, `observedAt`, 15-minute `expiresAt`, draft identity once created) *before* it runs the canonical commands. The canonical `social_post` command derives entirely from that observation: `commandKey` carries the observation instant, the attestation `checkedAt/expiresAt` are the observation values, content is the exact plain copy plus the reviewed canonical URL (`text/plain`), source system `relaunch72.seo-blog`, item `brand:article:network`, version `articleVersion:packSha`, metadata `brandId/articleId/articleVersionId/articleContentSha/canonicalUrl/packSha/network/observationId`. A retried request therefore replays byte-identical commands; a lost approval resumes from the stored draft identity without a second version; an expired observation yields a new observation and a new command, never an extended old one. The shared company-content idempotency validator is unchanged. The central runner calls `app_private.seo_blog_assert_article_promotion(...)` (0132) in the same transaction as every draft/approval command, so the parent article tuple is guarded at the database.

### Per-brand accounts, registry and dispatch (0132)

- A brand registers its own Zernio profile (`seo_blog_register_zernio_profile`, unique per profile, PP's env profiles refused) which creates/reuses that brand's live `provider_connections` row; the Social tab then prepares the brand's one-use OAuth handoff with the existing 0074 intent/preparation/callback functions under the brand workspace. Account-lifecycle webhooks resolve the owning brand by profile digest (`seo_blog_zernio_profile_workspace`) and are verified against that brand's own credential binding; PP's path is byte-for-byte unchanged.
- `seo_blog_register_social_binding` admits only an account the provider confirmed connected under that brand's profile/connection (foreign accounts raise `42501`), with owner-set caps 0–24/day and 0–300/month; **0 means off**. Revocation and caps are re-checked at effect time by `zernio_calendar_job_cap_ok`, which keeps the exact 0085 `≤1/≤3` predicate for jobs without a caps row (PP legacy) and uses `LEAST(enqueue caps, current caps)` for registered jobs.
- Planning and enqueue (`seo_blog_create_promotion_planning_intent`, `seo_blog_enqueue_zernio_calendar`) use the existing intent/target/revalidation/receipt/lease/call-boundary tables with registry hash contracts `relaunch72.seo-blog-zernio-calendar-command/v1` and `…-job/v1` that embed the brand's caps label and binding id; 0097's literal `daily=1;monthly=3` hashes and 0101's PP-only planner are untouched. Holds (`55000`): caps off, cap already used, Instagram without a real approved image. LinkedIn text is independently eligible.
- The SEO worker (`r72_content_command`, worker actor) performs just-in-time attestation: `seo_blog_attest_due_promotions` re-verifies the exact parent (current version, digest, URL, verified public, latest approval, no cancellation) within the 10-minute window and writes a **15-minute** proof; a changed parent cancels the slot (`seo.parent_changed`), a passed window expires it. Proofs cannot be refreshed after expiry: a late job holds (`needs_attention`) and nothing is sent.
- The Zernio calendar worker runs PP's pinned cycle first and, only when idle, iterates `seo_blog_social_dispatch_targets()` (active bindings with caps > 0) with a per-brand repository, per-brand posting targets and a text-only media resolver; at most one operation per cycle overall. PP's workspace is never re-bound from the registry.
- 0132 also re-creates `claim_zernio_calendar_job` with the exact 0085 body plus `#variable_conflict use_column`: the issued function returns a `job_id` column and writes `ON CONFLICT (workspace_id, job_id)`, which PL/pgSQL rejects as ambiguous the moment any job is claimable. This defect predates this run and affects PP's own lease path; the first real lease in the journey test exposed it.
