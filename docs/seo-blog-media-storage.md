# Private media, durable image admission and reviewed public use

This module adds private media storage and source-specific database capabilities. It has no supplier client, scheduler, HTTP route, worker producer or application UI. Migration0136 starts image spending **disabled**, with all operator limits zero. Nothing here configures a price, activates generation, approves content or publishes an article.

## Durable objects and privileges

Six workspace tables retain assets, preparations, immutable command receipts, owner use authorizations, publication/release bindings and explicit withdrawals. Assets reference the existing20MiB SEO blob store by composite workspace/blob identity. Candidates are limited to8MiB and remain unmeasured/unapproved. Prepared JPEG variants are limited to600,000bytes,1.5MP and the three reviewed profiles. The SQL boundary verifies byte digests, bounded preparation receipt/recipe metadata and exact tuple relationships; it does not replace the reviewed decoder or canonical owner quality review.

`seo_blog_image_attempts` is a seventh workspace table. It preserves immutable intent/job/nonce, original claim owner/epoch, request/source/profile/visual digests, UTC allowance period, conservative integer microusd reservation and trusted operator policy snapshot. Receipt history is append-only; final conflicting receipts fail. Cancellation, retries, new claims, policy edits and a new month cannot erase or reuse an admitted nonce.

The eighth table is a private singleton operator policy/admission row. It is intentionally outside the workspace registry. Trusted operator changes require a new configuration version; the database derives its digest. Workers may read safe configuration through a function and may increment the admission epoch only inside the admission function. Runtime roles receive no policy-table grant, cap update API, function-owner membership or runtime `SET ROLE` capability.

The NOLOGIN/NOINHERIT `r72_seo_media_definer` owns fixed-search-path functions. It does not inherit `r72_owner`. It has narrow new-ledger privileges, blob insertion and SELECT-only access to existing source/jobs/usage/canonical history. Legacy identity-column UPDATE privileges allow row locks on brand/article/publication; no capability mutates those columns. It receives **no new INSERT/UPDATE grants on legacy jobs or usage**. The existing content-command client performs those writes under its existing permissions.

All seven workspace tables use forced RLS and the workspace registry. Runtime roles cannot enumerate the new tables. PUBLIC execution is revoked from every new helper/wrapper. `r72_content_command` receives only named application wrappers; `r72_web` receives only `read_released_seo_media(releaseUUID,exactSHA)`. Trigger creation uses temporary migration-owner EXECUTE grants, revoked immediately afterwards. The function owner's temporary schema CREATE grant is also revoked.

## Image-job start and receipt APIs

`readImagePolicy()` returns the current trusted version/digest/configuration. Reservations mean headroom, not supplier invoices. No missing supplier cost or token count becomes zero.

`readImageSourceSnapshot(workspace,article)` returns the `seo-image-source-v1` database recipe. It contains the latest confirmed profile, current immutable article identity and latest active knowledge references with text digests. The hashes are opaque database fingerprints, **not JavaScript programmeSha values**. Initialization, start and apply compare the same structured snapshot/DB recipe.

`initializeImageIntent(workspace,input)` creates an existing-kind `write` job with `payload.stage='image'` and `payload.image.schema='relaunch72.seo-image-intent/v1'`. It stores the private frozen command, source snapshot and policy expectation. Actual user requests require a genuine current owner session. Automatic initialization uses the true worker and only the current profile's confirmedBy UUID as active managing sponsor, with ongoing production/image opt-in/current facts checked. Initialization cannot grant a provider call. Existing old workers fail closed on the unknown image stage.

Initialization serializes under the brand lock. Active identical source work coalesces across different command UUIDs. Automatic production retains one intent per exact article version across terminal states. A new manual paid intent after an admitted start requires explicit `confirmedNewIntent` and the server-validated authoritative latest `replacesIntentId`; no old nonce/reservation is erased. Append-only request aliases, capped at128 without dropping history, bind each command to actual requester/origin/article/version. `recoverImageIntentRequest` queries durable aliases before rebuilding a now-stale source, profile or prompt; it is receipt recovery, never a new provider grant. A conflicting command tuple rejects, and alias overflow holds instead of creating another paid task.

`commitImageAttempt(input)` is the coordinator-facing start API. It returns `admitted` **only after a successful COMMIT acknowledgement**. Its inner `reserveImageAttempt(t,input)` is provisional and exists only for same-client composition. It locks brand, then its own job, then the singleton global gate. It increments the gate epoch before aggregating other attempt rows without locking other brands. This serializes READ COMMITTED decisions and makes stale SERIALIZABLE snapshots conflict.

The new attempt, exact job-start nonce projection and one `images` usage debit commit together. A deferred INSERT-only constraint checks exact job/claim/nonce and exactly one amount1 debit in the recorded UTC period. A narrow partial UNIQUE index protects only the newly introduced `seo-image-start:` reference namespace. Existing usage references are unchanged; migration refuses a pre-populated new namespace instead of silently adopting data. Missing/wrong/duplicate debits fail the transaction. Later cancellation does not re-run the historical admission constraint.

Current-period reservations **or** older unresolved reservations consume global monetary headroom, counted once. Older unresolved starts also retain concurrency and brand allowance across month changes. Known completed reservations remain in their original month; they are not automatically refunded. Only an explicit trusted, audited operator resolution can release old uncertainty. It never makes the old nonce reusable. Default disabled/zero policy and brand image opt-in hold fresh starts truthfully.

An ambiguous start COMMIT throws; it is never a grant. A later read returns `existing_started`, `existing_receipt` or a hold. Exact receipt recovery precedes fresh readiness/policy admission checks, so removed provider configuration does not cause another call.

`commitImageAttemptReceipt(input)` owns a transaction; its inner same-client `recordImageAttemptReceipt(t,input)` binds the original attempt/nonce/request and original worker claim. Raw bytes, actual byte SHA, safe transport receipt and accounting state persist atomically **before any decode/crop**. Candidate rows require a real same-workspace admitted attempt. Manual uploads use the separate genuine-owner wrapper and cannot pretend to be generation attempts.

Reserved and actually received request SHAs are separate evidence. A mismatch stores safe actual/request and observed candidate SHA only, attaches no candidate bytes and holds the uncertain reservation. It cannot apply or trigger another call. Safe receipt fields allow only enum outcomes/codes, digests, bounded HTTP status and nullable nonnegative token counters; no prompt, credential or raw supplier body belongs in a receipt.

Late matching receipts survive cancellation, lease changes, sponsor removal and policy changes. They do not change job state or clear a cancellation. Receipt replay is DB-only and idempotent. A stale original worker cannot adopt a newer claim; `checkImageApplyEligibility(t,currentClaim)` allows known-receipt local recovery under the genuinely current lease after rechecking snapshot, sponsor, pause and current operator policy. `applyPreparedImageBoundary(currentClaim,callback)` additionally verifies exact derivative UUID/SHA/profile rows against this attempt's real candidate and gives the SQL-only callback the locked current job and verified private preparation. The callback's private article proposal and truthful job outcome commit or roll back together. It must never approve, publicly release, call a provider or acquire another pool client.

Local preparations use stored bytes and `commitPreparation`. Use a stable command UUID per exact source/recipe; retries reuse it. New focal/crop choices produce a new local preparation command, not a paid call. Invalid JPEGs remain private candidates with an honest rejected preparation receipt. Private asset storage/preparation does not authorize a public URL.

## Canonical quality and noncircular public release

1. `reserveMediaUse(ownerSession,article,asset,presentation)` preallocates a stable release UUID and absolute URL while it remains404/private.
2. Put that exact URL/alt into the final immutable ArticleVersion **before** target/delivery hashing and article owner review. Target review can create another version; bind the final version explicitly.
3. `getCanonicalManifest` derives the image quality manifest from actual stored bytes/recipe/dimensions/MIME/alt/provenance. Review the private actual pixels and manifest through the existing canonical `kind=image` version/request/decision mechanism. No parallel `approved=true` record is introduced.
4. `recordOwnerImageAuthorization` requires the real active owner session, final current article/version/content SHA and exact selected canonical approval. The latest eligible request of that exact image version must be approved. An explicitly selected historical approved version remains usable after a different newer version is rejected; there is no automatic fallback. Existing same-version reapproval guards remain unchanged.
5. The canonical source is `relaunch72.seo-media`, itemID is the immutable asset UUID, and sourceVersion is `media:v1:<assetSHA>:<enumeratedProfile>:<SHA256(UTF8 exact trimmed validated alt)>`. It contains no prospective-use UUID. Identical explicitly selected pixels/presentation can reuse an exact old quality approval, while every new use still requires fresh owner authorization.
6. `releaseForPublication(t,workspace,input)` runs on the **same client** as the established approved publication-begin transaction, after its valid locked decision and before commit. It checks exact article/version/image URL/alt, authorization/asset, selected quality approval, pinned target/destination semantics, current owner/pause/checks/publication policy and stable reviewed intent. Forv2, reviewed intent is the immutable target deliverySha; legacy uses contentSha plus all explicit tuple checks. The future timestamped requestSha is not an owner-review token.

Every new write/resend additionally calls `assertPublicationMediaEffect(t,workspace,input)` BEFORE that receipt-first hook. The fixed assertion mode runs the same fresh predicates under the same brand SHARE→article→publication locks, cannot take a historical receipt shortcut and cannot insert a release. Reconciliation, receipt lookup and public serving do not call it. Thus a valid retry retains identical release bytes/identity; revocation/withdrawal/stale source stops a fresh begin even when its historical receipt still exists. Missing publication policy fails closed; explicit approved policy must name this version, and auto policy must capture its actual permitted flags.

The public URL UUID is known before approval. An internal append-only binding records each actual publication operation using that reviewed URL. It is valid for a prepared reviewed publication intent; it need not wait for the website to be live. A crash or uncertain website outcome does not silently revoke an image that may already be live. Publication receipt replay precedes fresh eligibility and preserves identity.

`readReleasedAsset(releaseUUID,exactSHA)` reads only the durable approved release snapshot and exact unmodified bytes. It does not depend on today's editor version, profile, membership or latest image request. New unapproved drafts and removal of the original approver do not break old public heroes. A new use cannot borrow a different article's reservation.

`withdrawAssetOrRelease` requires a current genuine owner session and appends a revocation. It stops future origin serving and fresh release admission. It cannot recall a previously cached response. The later HTTP composition must return only the fixed JPEG MIME and exact returned bytes, and404 for absent/withdrawn/unreleased tuples.
