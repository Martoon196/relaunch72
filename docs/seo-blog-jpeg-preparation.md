# JPEG preparation component

This is an isolated, non-live preparation component for the later campaign/media workflow. It does not generate images, fetch URLs, store assets, grant approval, publish posts or make Instagram delivery work. No engine, router, shared SEO contracts, database schema or provider composition is connected to it yet.

`prepareJpegVariants` accepts bytes and a supported format selection/focal point. It snapshots the original, checks the complete JPEG marker structure and dimensions before the allocating decoder, rejects non-identity EXIF orientation rather than cropping rotated pixels incorrectly, then decodes once and prepares derivatives synchronously and sequentially. The original bytes and SHA256 remain preserved. Each returned byte-buffer access is a copy, so the content-addressed objects cannot be mutated by the caller.

Initial formats are explicitly limited to blog 1600×900, Instagram portrait 1080×1350 and LinkedIn landscape 1200×627. These are preparation recipes, not a claim of universal platform requirements or connected delivery. Cropping uses one aspect-preserving scale with a clamped focal point. Each derivative records recipe version, profile, focal point, crop, actual encoder quality, source digest and its own exact byte digest. EXIF/GPS/comments are omitted from derivatives.

Limits are 8 MiB input, 8 megapixels, 8192 per source dimension, 128 MiB codec allocation guard, three derivatives maximum, 1.5 megapixels and 600,000 bytes per derivative (the stricter canonical social-image limit). Quality attempts are bounded to 85/70/55; failure to fit is explicit. Byte limits alone are not a whole-process memory guarantee. The caller must preserve this synchronous/sequential resource policy when integrating the component; do not launch uncontrolled parallel image jobs. Inputs with unsupported JPEG encoding, malformed marker structure, truncated data, unknown orientation or unsafe dimensions fail without an external effect.

The sole added codec is exact `jpeg-js@0.4.4`, BSD-3-Clause, with no runtime dependency or lifecycle-script additions. Official npm tarball and integrity are pinned in the lockfile; the CycloneDX SBOM adds exactly one external package. Upstream: <https://github.com/jpeg-js/jpeg-js>. The codec's strict decoding, resolution limit and allocation guard are enabled explicitly. Existing unrelated `fast-uri@3.1.6` audit findings were retained and reported separately; no blanket dependency upgrade was performed.

Focused tests use actual encoded JPEGs and decoded pixel colours to verify focal crops, exact output dimensions/digests, source ownership, metadata removal, orientation rejection (including post-scan EXIF), oversized-header rejection before decode, malformed inputs, decoder reuse and bounded quality attempts. Full normal release checks belong to the eventual integrated exact source, not this preparatory component alone.

Integration must add genuine brand-scoped immutable storage, paid-generation budgets/receipts, human review of exact asset versions, canonical approved media, channel/account checks and parent-article publication dependencies before advertising a complete campaign feature. A digest or in-memory image is not a durable storage URL or an approval.
