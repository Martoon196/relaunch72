# Website targets and public delivery (009B)

This schema-neutral consumer extends the existing blog programme. It does not generate articles, enable public approvals, spend provider credits, migrate article URLs, create arbitrary website routes or change social-account authority. Existing content API v1 `/blog` and configured static publishing continue to work. Existing 009A guidance is not silently converted into v2 website approval.

## Website and owner contract

The signed content API connection check can return protocol v2 capabilities. The consumer validates the exact configured HTTPS origin, stable website UUID, opaque website-issued capability digest, installed single-segment roots and exact URL patterns, category limit and same-origin sitemaps. An unknown/malformed capability object fails the connection check. Plain `ok:true` is legacy support, not evidence of categories or another root. Optional website namespaces can be absent: only actually advertised roots appear in the owner picker. The capability receipt is a typed private record field, separate from editable string configuration.

Root/category guidance approval is a genuine current owner command using the existing selected portal session and target-brand membership. It checks the current website capability, current inventory recommendation and brand row version. Stable structure/category UUIDs are derived server-side from the brand, connection and site lineage; category identity additionally binds its root and slug. Recommendation IDs are retained as provenance but do not control an archive identity. A timestamp-only rescan or changed recommendation identity cannot reassign an existing archive. New or changed category addresses require an explicit acknowledgement; earlier archives and article URLs stay fixed.

A new unpublished article automatically receives a proposed first target from the current owner-approved v2 default, without an extra target-save chore or model call. Its version insertion rechecks the exact structure version/hash, destination/capability identity, current sponsor/profile and pre-generation knowledge snapshot under brand/article/source locks. Stale input cannot attach a proposal. Empty membership is labelled No category selected. Existing pinned targets survive body edits/regeneration and the ordinary exact-version approval/autopublish policy remains in force.

An article's optional website-target action chooses only category IDs from a server-stored catalogue. The atomic store command locks brand, article, publications and destination; it revalidates the genuine owner/session and expected version. It appends a new immutable version containing the complete site/root/canonical/index/catalogue/membership snapshot and delivery digest, resets exact-version approval, and retains body, citations, knowledge and previous versions. Target review performs no model generation or publication. Ordinary content edits retain an existing target when its slug remains unchanged and update the delivery digest; publication approval follows the existing exact-version controls.

A published article keeps its first canonical URL and slug. Changing the default root affects new articles. Existing v2 articles can review and use their stored historical root/catalogue after the default changes. Legacy /blog updates stay v1 unless an owner explicitly reviews v2 adoption. Adoption needs owner-approved guidance for that original root or a genuine stored historical target; a new default never invents a fallback lineage. Moving an existing article is not part of this package.

The article delivery projection carries its owning publication operation ID, independently of the editor version. A late receipt may resolve its own delivery claim while retaining a newer unapproved draft, but cannot overwrite a newer operation’s state. Legacy fallback requires a sole matching operation and attempt.

At publication begin the existing lock boundary copies the exact authorised sealed connection, article target, brand/locale and publication timestamp into a private publication snapshot. `websiteSnapshot.reviewedIntentSha` copies the reviewed v2 delivery digest (legacy fallback: immutable article body SHA), while `requestSha` also covers the begun timestamp. The legacy fallback is body/version binding, not destination/catalogue approval or an authorisation token. Future image release must additionally check exact article/version/content digest, image URL+alt, asset use, genuine owner authorisation and pinned destination/target; this package releases no media. Provider calls occur only after commit. Reconciliation uses this original operation and snapshot, even if mutable defaults change. Fresh resends still require current controls and unchanged connection/target capability. The owner-facing projection omits the private connection snapshot. Content API v2 sends the exact relative-root `target` contract; status must agree with its canonical, protocol and immutable target before a stored receipt is accepted. Website acceptance is followed by independent public checks.

## Independent evidence

Each publication records bounded, timestamped dimensions independently:

| Dimension | Required public evidence |
|---|---|
| Article | HTTP200 complete page at the exact final URL, one real head version meta, and one exact canonical link |
| Root index | Exact article link, following bounded same-archive `rel=next` pagination |
| Categories | Selected category archives link to the article and the article links to those reviewed category archives |
| Sitemap | Served exact canonical location, occurrences, observed lastmod and traversal completeness |

HTML comments or a version marker on an unrelated page cannot establish success. A missing first-page link cannot establish archive absence. Sitemap indexes follow at most20 documents, each bounded to3MiB and50,000 entries, with namespace/CDATA support and no DTD/entity expansion. Invalid, failed or incomplete reads are `unknown`/`incomplete`, not absence. A complete traversal can report a pending or duplicate location. These are delivery observations, never a promise of search indexing.

A verified article with pending index/category/sitemap evidence remains published. Social eligibility still depends on the exact current article/version/public URL and existing social rails. If a later article/canonical check disagrees, current delivery is held as unknown until exact proof returns. Secondary indexing evidence cannot substitute for article proof.

Secondary observations run at most12 times per observation intent:30 seconds initially, then5 minutes. Explicit owner recheck starts a new read-only intent. Stable existing-kind `publish` wakeups are inserted in the same transaction as pending publication evidence, so an unscheduled published-only brand remains discoverable. The handler distinguishes observation and repair payloads from ordinary publication dispatch. No new job kind, payload `stage`, state enum or discovery privilege is added.

## Static catalogue ordering

Static v2 publication maintains `.relaunch72/seo-blog/<stableSiteUUID>.json` in the same nonforce tree as the article, index, category archives and sitemap. The bounded512KiB file contains only public source/site/schema markers, known structure revisions/digests, permanent category-to-lineage/root/slug ownership and newest archive labels. It contains no guidance, prompts, credentials or private receipts. Unknown older revisions, conflicting known revisions, reused IDs/addresses, corrupt/unowned files and missing history on an existing managed site hold the write. History is never automatically forgotten to make a publication fit. Initial namespace checks are bounded and fail closed when incomplete.

A known older reviewed target can add its article membership without restoring an older shared label. Historical articles keep the labels in their immutable reviewed target; shared archives show the newest accepted label. Empty archives remain noindex and are removed only from owned sitemap entries. The catalogue's source blob digest and exact repository head are pinned when building the nonforce commit; a concurrent human change forces re-read, never force-push. Sitemap-only repair never changes this catalogue.

## Sitemap-only recovery

PP's v2 website advertises `repair.sitemap:false`: its sitemap is a dynamic website projection. The consumer offers recheck and an integration remedy, with no invented repair endpoint and no article republish to fix XML.

The static adapter supports a separate owner repair intent. It pins command nonce, publication/version/target digest and the exact repository sitemap source digest. A worker under its real principal rechecks current requesting-owner eligibility, current published version/URL, connection and pause under the publication lock boundary. Before writing, the adapter reads the current repository article marker and exact sitemap source, then creates one nonforce commit touching only the owned sitemap URL block. It preserves unrelated XML bytes/lastmod, article/index bytes and the original publication timestamp. A different source version or human branch change refuses the write.

The intent and worker wakeup commit atomically. Duplicate workers share the intent; known commit receipts retry only database persistence. An unknown acknowledgement never causes an automatic second commit. Started/unknown recovery is read-only, survives pause and cannot be cleared by a generic Retry or task cancellation. It has at most6 read-only checks with saved30-second/5-minute backoff, then an explicit uncertain hold. A genuinely new owner intent after uncertainty requires acknowledgement and a new nonce; the original history remains. Cancelling a queued repair before begin holds it without writing.
