# Read-only native authority assembly (011C)

The new controller/view assemble the approved011B proposals from genuine existing SEO engine reads. They provide a native brand content fragment for later central route integration. No route is installed by this component; no independent release or durable queue is claimed.

## Access and input assembly

AuthorityProgrammeReader is an actual Pick of SeoBlogEngine's getBrand/getProfile/listKnowledge/getInventory/listArticles/getArticle. Every call carries the same genuine actor and target brand. Missing website, profile, confirmation, inventory or matching source references produces a specific read-only status and an existing target-brand Setup link. Permission errors401/403/404 propagate, including revocation during batched article reads. Other read failures become a safe503 without database/credential details. No provider, fetch, source refresh, profile extraction, plan, settings, approval or store method exists on this interface.

Logical document versions are selected before testing active state; retiring a later version never resurrects an older upload. Text-bearing references match the actual profile extraction contract. Visual-only context changes receive a guidance review notice without declaring existing facts invalid or requiring a new paid extraction. These strict snapshot checks are preparation rules, not a claim that the reads are atomic or that any future effect is authorised.

The returned model contains only a minimal brand header, dated review, grounded briefs, status and coverage. Raw documents, blob references, brand settings, article bodies and sealed website snapshots do not enter it. Private owner-confirmed facts that intentionally form a brief retain their source references. Optional supplier AI observations remain absent because this allowed read interface has no genuine stored authority measurement; no provider result is fabricated.

## Published evidence and coverage

At most30 published articles receive additional detail reads, in batches of3. Remaining coverage is explicit. Published evidence is derived from article.publishedVersionId and publishedUrl plus the matching immutable version, even when a newer unapproved draft exists. A published operation must match brand/article/version/content SHA/public URL/state. An owning deliveryPublicationId is used only if it matches that published tuple; otherwise a sole matching operation is accepted. Multiple matching historical operations remain ambiguous rather than being selected by UUID or timestamp. Only the public projected websiteDelivery is passed to011B; missing or malformed evidence is counted separately and never replaced with an invented observation.

The controller performs no live page check. All displayed delivery evidence retains its recorded dates and complete/unknown states. A future mutation or queue adapter must independently acquire current locks, permissions and source hashes.
