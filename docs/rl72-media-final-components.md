# RL72 media — final pre-integration components

All modules belong to the same Creative Studio, canonical identities, source catalogue and existing Zernio worker. New SQL remains in `orchestrator/src/creative-studio/migration-drafts/`. Claude retains routing, production schema numbering, configuration and deployment. No live provider, email, payment or publication was performed by this build.

## 1. Private sources up to 1 GB

`PrivateMediaFiles` is an actual streaming private-filesystem backend, not a buffer placeholder or public CDN. It requires an absolute, private, non-symlink durable directory. Parts are <=8 MiB, immutable after atomic commit, with exact whole-file SHA256 verification. File reads reject symlinks, changed sizes/digests and cross-workspace key substitution. A workspace can stage three uploads and retain up to 10 GiB of canonical private source data. Sources share `creative_media_source_videos`; small PG blobs remain <=20 MB. Final render outputs retain their existing <20 MB ceiling.

`PgPrivateObjectSources.begin/status/part/complete/cancel/source/range` enforces the genuine selected owner session at every operation. Source metadata stays `awaiting_probe`. `PgPrivateObjectProbeWorker` verifies the physical file and performs a real bounded FFprobe before recording technical readiness. The existing one-shot local render worker now accepts private-object references and calls `renderLocalVideoFile`; the graph/encoder/output/approval pipeline is shared. `media:worker probe|render-local|tick` supports the configured backend.

**Claude configuration:** `CREATIVE_MEDIA=enabled`, `RL72_MEDIA_PRIVATE_FILES_ENABLED=true`, `RL72_MEDIA_PRIVATE_FILES_ROOT=/absolute/private/durable/path`, existing worker/local-render flags. The same directory must be visible to the authenticated upload server and isolated worker. This implementation needs durable disk; it does not provision a disk, bucket or service. Never point it at a public static directory. Configure disk capacity and supervise the prepared cleanup command before release. `PgPrivateObjectCleanupWorker.sweep` and manual `media:worker -- cleanup-objects <workspace>` remove expired/cancelled staging and uncommitted assembly only; completed canonical sources are excluded. Batches are <=10 and cancelled sessions are periodically rechecked to recover crash/race leftovers. No scheduler is activated by this build.

**Prepared HTTP surface:** GET `creative/object-uploads` -> `creativeMediaLargeUploadPage`. Serve `MEDIA_LARGE_UPLOAD_SCRIPT` at `/portal/seo-blog/media-large-upload.js`. POST `creative/object-uploads/begin` takes bounded JSON `{uploadId,byteLength,sha256,fileName,mime,rights,evidenceSha256,rightsConfirmed}`. GET `creative/object-uploads/:id` returns persisted state and physical-part checksums for resume. PUT `.../:id/parts/:part` accepts <=8,388,608 raw bytes. POST `.../:id/complete|cancel` calls corresponding methods. Owner/private source byte streams use `.source` then `.range` plus the existing HTTP single-range helper and private/no-store headers.

The browser uploader computes a full-file checksum incrementally in a Web Worker, and uploads bounded chunks; it never calls `file.arrayBuffer()` on the whole large file. CSP needs the owned script and generated `worker-src blob:`. The main UI stays responsive. Existing small upload remains available as its own pilot route.

## 2. Native video release into existing Zernio worker

Canonical handoff versions use kind `video`, MIME `video/mp4`, a UTF-8 exact-review manifest and actual MP4 SHA with a dedicated `rl72-native-video/<workspace>/<output>/<sha>.mp4` canonical media reference. The wrapper recognizes only this namespace and delegates all other assets to the existing resolver. Existing public-social planning already accepts separately approved video media; use that canonical planner to attach the approved video to a separately approved post/caption and saved target job. The existing transport already sends `type: video`.

`PgNativeVideoReleaseOwner.decide` adds explicit owner permission for one saved canonical job and exact video version, separate from private review. SQL checks current video bytes/provenance, latest private review, current brand digest, latest canonical version, genuine current canonical approval, fresh source evidence, exact reviewed publication copy and attached job media. Withdrawals are append-only; re-review or changed brand/content invalidates the earlier release.

`PgNativeVideoReleaseWorker.load` is granted only to `r72_owned_social_worker_command`. It refuses another job/workspace, unleased work, missing consent, stale evidence and withdrawn releases. `createNativeVideoMediaResolver` wraps the existing media resolver. It reuses the existing `posting.prepareMediaUpload`, verifies the approved R2/Zernio destinations, rechecks release before and after uploading, and returns a native MP4 URL to the same calendar worker. It creates no alternate scheduler or posting transport. A new draft trigger rechecks native video readiness as the existing job enters `calling`, so publication cannot proceed with stale/withdrawn media.

**Claude hook:** wrap the existing calendar media resolver with `createNativeVideoMediaResolver({store:new PgNativeVideoReleaseWorker(existingOwnedSocialWorkerPool,requestId),posting,fetch,legacy,env})`. Keep the canonical planner/lease/caps/mark-calling/settlement/reconciliation unchanged. Resolve media through this wrapper before dispatch. Enable only after review with `RL72_MEDIA_VIDEO_RELEASE_ENABLED=true` and `CREATIVE_MEDIA=enabled`; the existing provider-effects and emergency-pause gates still belong to the canonical worker.

Embed `nativeVideoReleaseForm` in the saved canonical job detail using its actual selected-workspace snapshot. POST `creative/video-releases` must enforce owner session and CSRF; parse `jobId,contentVersionId,commandId,action,consent`, then call `.decide({workspaceId:brandId,...})`. No browser-supplied workspace or provider target is authority. A withdrawal blocks future effects, and cannot undo an external upload/post already accepted.

## 3. Standalone signup and onboarding

`PgAffiliateStudioSignup` calls a bounded signup capability on the existing `r72_provisioning_command` pool. It reuses `provision_customer_workspace_with_setup_delivery`, so pending users, organizations, memberships, one-use password setup and AES-GCM setup outbox are canonical. It creates the new brand with zero generation allowances. It returns only a generic accepted response: no password, setup token, user/workspace IDs or account-existence disclosure.

Existing identities never gain a new membership or password-reset credential from signup. Retries reuse the first outbox record. Operator-reviewed terms, a global daily cap and deployment-keyed source/hourly caps are checked atomically. The signup table retains hashes and receipt identity; email remains in the canonical users/encrypted delivery machinery. `completeAffiliateStudioSetup` delegates to existing `PortalAuthService.completeSetup`, including its one-use token and normal opaque session. After setup the existing brand, product, footage and billing screens perform onboarding; no parallel auth or customer account store exists.

**Claude hook:** public GET/POST `/affiliate-studio/signup`, view `affiliateStudioSignupPage`, flag `RL72_MEDIA_STANDALONE_SIGNUP_ENABLED=true` plus `CREATIVE_MEDIA`. Enforce normal anonymous CSRF, same-origin and request limits. Use the server-observed source through `mediaSignupSourceHash(observedSource,32ByteDeploymentSecret)`; never accept `sourceHash` from the form or untrusted forwarding headers. Inject canonical `PgSetupDeliveryService.prepare`. The existing setup-delivery worker handles delivery only after configuration/review; this service never sends email itself. Operator policy starts disabled with zero limits under `app_private.creative_media_signup_policy`. Match its current `terms_version`; provision actual legal pages separately before enabling signup. Existing `/portal/setup` and login remain canonical.

## 4. Direct merchant pages and observed clicks

`PgAffiliatePublicationOwner.publish/list/withdraw` authorizes an exact current product revision, current programme/site/tag evidence and direct-link SHA for a specific public page. Publication requires explicit consent and the operator-configured public origin to match the owner's registered site. Changing the product or withdrawing the page makes the public reader return unavailable. These are owner assertions, not independent merchant-account verification.

`PgAffiliatePublicPages.page` validates the direct Amazon UK link again before rendering `affiliateProductPage`, which includes the required affiliate disclosure and no invented price/specification/sale. The merchant URL and assigned tag stay direct: no first-party redirect or substituted tag. Its optional beacon carries only a short-lived HMAC capability with page ID, product revision, random page-load nonce and expiry. SQL verifies HMAC, current evidence/page, expiry and nonce uniqueness; requests cannot fabricate counts with unsigned or replayed tokens. The template never intercepts merchant navigation. No cookie, visitor ID, email or IP is put into the click record. A daily per-page cap bounds ingestion. Counts mean observed outbound-click beacons deduplicated per page load, not unique people, orders, verified purchases or commissions. Merchant reports remain the separate earnings source.

**Claude hook:** owner POST `creative/product-pages` / `.../:id/withdraw`, owner/CSRF protected, uses `PgAffiliatePublicationOwner`; owner GET composes its `.list` with current products/evidence. Public GET `/affiliate-studio/p/:id` uses only the canonical `r72_public` pool and `.page`. Render the returned page/token; return 404 if unavailable. Enforce the configured origin and `Cache-Control: no-store`, `nosniff`, noindex and the intended CSP/referrer policy. Serve `AFFILIATE_CLICK_SCRIPT` at `/affiliate-studio/click.js`. POST `/affiliate-studio/click` accepts <=300 plain-text bytes and calls `.click(token)`; use a non-disclosing 204 response and endpoint rate limits. It requires no owner session because the signed capability is its narrowly scoped authority.

Flag `RL72_MEDIA_AFFILIATE_PAGES_ENABLED=true` plus `CREATIVE_MEDIA`. Set the same reviewed 32-byte random signing key in the service and `app_private.creative_media_link_public_policy`, with exact public origin and enabled policy. The public reader returns only its key digest, not the key; a mismatched service key fails closed. Policy starts disabled. Programme/site eligibility and legal content must be genuinely checked before enabling distribution.
